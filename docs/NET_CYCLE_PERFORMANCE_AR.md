# إثبات الدورة الاصطناعية وقياس أحجام متزايدة

الأداة: `scripts/check_net_cycle.py`. تستخدم خدمات النظام ومسارات HTTP الفعلية وقواعده الموقعة، دون إنشاء لقطات مالية وهمية. تشغل كل حجم في عملية مستقلة وقاعدة SQLite مؤقتة جديدة، وتزيل قاعدة البيانات والتخزين المؤقت بعد القياس. لا تتصل بقاعدة التشغيل ولا تشغل migrations.

## ترتيب التنفيذ

يجب إثبات اختبار الدورة الواحدة واختبار الملف متعدد الحالات قبل تشغيل الأداة. الأداة نفسها تبدأ بخدمة واحدة صحيحة، وتشمل إنشاء حالة مراجعة، والاقتراح، ومنع الاعتماد المالي من حساب Super Admin التقني، ثم الاعتماد بحساب مخول مستقل. لا تنتقل إلى حجم أكبر عند فشل أي تحقق.

بعد نجاح الخدمة الواحدة تقيس الأحجام `10` و`50` و`100` خدمة. تتناوب الحالات الاصطناعية بين المقبول، وفرق سعر NET مثبت، ونقص ربط فاتورة، واختلاف هوية يحتاج مراجعة. لا تحدد هذه الأحجام عدد المطالبات الفعلي للجهة، ولا تستنتج حجم المعالجة من قيمة المطالبات المالية.

## التشغيل بعد اجتياز بوابة الإثبات

من جذر المشروع وببيئة Python التي تحتوي اعتماديات الاختبارات:

```bash
python scripts/check_net_cycle.py \
  --sizes 1,10,50,100 \
  --output docs/evidence/net-cycle/performance.json \
  --artifacts-dir /workspace/library-files/net-cycle
```

ينشئ خيار `--artifacts-dir` نسخًا اصطناعية قابلة للفحص: ملف Excel الأصلي، وPDF الفواتير، وZIP المخرجات الأربعة لكل حجم. هذه بيانات اختبار وليست فواتير أو موافقات مؤسسية حقيقية. يتطلب التشغيل اتصال TestClient المحلي المسموح في بيئة الاختبار، ولا يحتاج خدمة HTTP منشورة.

## ما الذي يُفحص

- استيراد Excel الفعلي، وربط الأعمدة، واكتمال كل سطر.
- PDF اصطناعي فعلي بصفحة لكل خدمة. ينفصل عدد المستندات عن عدد روابط الخدمات: ملف PDF متعدد الصفحات واحد، ورابط مستقل لكل خدمة مرفقة. حالات نقص الفاتورة تبقى بلا رابط، حتى إن احتوت الحزمة الاصطناعية على صفحتها.
- إعادة فحص المراجع، وتسجيل سياسة NET بتوقيع HMAC فعلي وحسابي اعتماد ومراجعة مختلفين، ثم التدقيق وPalermo-2.
- مقارنة كل نتيجة بالتصنيف المتوقع المحدد مسبقًا، وحساب الدقة ومصفوفة الالتباس ودقة واسترجاع كل فئة. الفئة غير الموجودة في حجم معين تسجل قيمتها غير القابلة للحساب `null`.
- خروج كل خدمة مرة واحدة في ملف واحد من `accepted.xlsx` و`rejected.xlsx` و`held.xlsx` و`review.xlsx`، مع السبب العربي «نقص المرفقات» للمعلقات المختصة.
- حفظ بايتات وSHA-256 لملف المطالبات الأصلي وPDF دون تغيير.
- اتزان الأرقام في اللقطات المالية المتحققة، وعدم خصم تحمل المستفيد مرتين. مثال السعر المطابق: إجمالي `1000` وتحمل `100` وصافي مقبول `900`. مثال الفرق: صافي مطالب به `1080` ومقبول مبدئيًا `900` وفرق `180`.
- عدم احتساب المعلقات أو المراجعة باعتبارها اعتمادًا ماليًا. المخرجات تبقى أولية حتى بعد إثبات مسار اعتماد بشري على حالة واحدة.

## القياسات وحدودها

يسجل JSON وقت الإعداد، والاستيراد، وإنشاء/استيراد PDF وربط كل خدمة، وإعادة فحص المراجع، وتسجيل السياسات، والتدقيق والتحقق، وتجميد المخرجات وتنزيلها. معدل الدورة يحسب من مجموع هذه المراحل بعد استبعاد تهيئة البيئة وخطوة الاعتماد البشري الخاصة بالحجم الأول. يسجل معدل التدقيق وحده كذلك.

يسجل أعلى ذاكرة للعملية المستقلة، بما يشمل مفسر Python والاستيرادات والإعداد والدورة. يسجل إصدار Python والمنصة وCommit المرجعي وحالة الملفات المحلية وبصمات الشيفرة ذات الصلة، لأن القياس قد يخص تغييرات غير محفوظة في Commit بعد.

النتائج تخص بيانات اصطناعية وSQLite وFastAPI TestClient على المنصة المسجلة. لا تثبت أداء PostgreSQL أو Windows أو Docker على اللابتوب، ولا حمل المستخدمين المتزامنين، ولا دقة OCR أو مطابقة محتوى الفاتورة تلقائيًا. تصنيف الفاتورة صريح من المشغل في هذه المرحلة. لا تمثل النتائج قبولًا مؤسسيًا أو SLA للإنتاج.

في تجربة الخدمة الواحدة ثبت أيضًا منع اعتماد الحساب التقني، ثم نجاح اعتماد حساب مستقل مخول. المخرجات الأربعة نفسها بقيت أولية في جميع الأحجام (`financially_final=false`).

محاولة إطلاق سابقة أُلغيت قبل استلام جلسة تشغيل أو دليل نتائج. لا تدخل هذه المحاولة في الأزمنة أعلاه ولا تُحتسب تجربة ناجحة أو فاشلة. القياسات الموثقة تخص التشغيل المكتمل المحفوظ في JSON فقط.
