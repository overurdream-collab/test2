# MCIAS — سياسة التوثيق الإلزامية وحفظ سياق المشروع (DG-001)

**الحالة:** سياسة تنفيذية معتمدة بطلب صاحب المشروع بتاريخ 2026-10-17.  
**المجال:** مستودع `overurdream-collab/test2`، كل الفروع، التطوير والاختبارات والتصميم والأمن والتوثيق وملفات التهيئة.  
**مبدأ الحوكمة:** لا تغيير بلا توثيق في **نفس Commit**، ولا اعتماد بلا اختبار مثبت، ولا ادعاء اكتمال دون دليل.  
**الاستثناء التاريخي:** التغييرات السابقة لخط الأساس `8bdb43fd467f5766ecaa8cbc48f379dea99e17cb` في الفرع الجاري أُنجزت قبل إصدار هذه السياسة، ولا يُعاد كتابة تاريخها؛ تسجل حالتها في نقطة التسليم الحالية. يتحقق الفحص الآلي من كل Commit جديد بعد نقطة الأساس.

## 1. التزام فوري بعد كل حفظ أو تعديل أو إجراء

كل خطوة تؤثر في الكود أو الواجهات أو بيانات الاختبار أو ملفات التهيئة أو المعمارية أو الوثائق أو المصادقات تُحفظ في Commit واحد ذري يشمل **معًا**:

1. التعديل المراد تنفيذه، بالحد الأدنى الممكن.
2. إضافة حدث جديد في `docs/MCIAS_V2_EXECUTION_JOURNAL_AR.md` بعنوان فريد `### HANDOFF-YYYYMMDD-NNN` ويحتوي **جميع الحقول التالية**:
   - `- Scope:` ما الذي تغير وحدود ما لم يتغير.
   - `- Why:` الطلب والسبب الهندسي/التجاري ورقم القرار إن وجد.
   - `- Files:` مسارات الملفات والجداول وواجهات API المتأثرة.
   - `- Tests:` أوامر الاختبارات التي نُفذت فعليًا؛ أو `NOT_RUN: سبب محدد`.
   - `- Result:` `PASS / FAIL / NOT_RUN / PENDING_CI` مع نطاق الإثبات. لا تُستعمل PASS قبل رؤيتها.
   - `- Risks:` الآثار الجانبية، الخصوصية، التراجع، والحدود غير المختبرة.
   - `- Next:` خطوة تالية واحدة واضحة ومالكها/شرط إنجازها.
   - `- Handoff:` كيفية استئناف العمل من نسخة الكود هذه وتبعياتها.
3. تحديث `docs/MCIAS_V2_CURRENT_STATE_AR.md` للحالة الحقيقية الحالية: المرجع، آخر ما تم، الوظائف المختبرة، القيود، موضع التوقف، الخطوة التالية، روابط PR والاختبارات.
4. عند تغيير سلوك أو API أو نموذج قاعدة البيانات: تحديث الدليل `docs/MCIAS_V2_DEVELOPER_START_HERE_AR.md` والمصفوفة `docs/MCIAS_V2_ACCEPTANCE_MATRIX_AR.md` والاختبارات. إذا لم تنطبق وثيقة، يُشرح السبب.
5. عند قرار معماري ذي أثر طويل: ADR جديد أو تعديل ADR مقترح، مع المقارنة والسبب والموافقة المطلوبة. لا تستبدل قرارًا معتمدًا بصمت.

**لا تحفظ الكود ثم تؤجل وصفه إلى نهاية اليوم**. يتطلب الفحص الآلي وجود سجل وتحديث حالة المشروع داخل Commit نفسه. أوامر `git add` لجميع الملفات ثم `git commit` واحد مناسبة؛ عند استخدام API مباشر يجب استخدام Commit متعدد الملفات/شجرة واحدة لا سلسلة Commits غير موثقة.

## 2. سجل لا يقبل التخمين أو إخفاء الثغرات

- كل ادعاء مرتبط بنتيجة فعلية، أمر اختبار، ملف، إصدار، Commit SHA أو رابط GitHub Actions. ظهور `PASS` سابقًا لا يثبت SHA جديدًا.
- صرّح `NOT_IMPLEMENTED`, `PARTIAL`, `BLOCKED_INSTITUTION`, `NOT_TESTED` كما هي.
- لا تحفظ أسرارًا أو كلمات مرور أو Tokens أو بيانات مرضى في GitHub أو سجلات CI أو لقطات الشاشة.
- لا تكوّن بيانات مرضى للتجربة؛ استخدم بيانات اصطناعية واضحة `SYN-`.
- لا تحذف السجل السابق أو تعدِّل أدلة الاختبارات لتبدو ناجحة؛ التصحيح حدث جديد يشرح الخطأ وتغييره. تاريخ Git هو المصدر التقني لتسلسل الحفظ.
- تاريخ سريان الشروط والعقود منفصل عن تاريخ تغيير الكود؛ تعديل القواعد المالية لا يغير مستندًا موقّعًا أو نتيجة تدقيق قديمة.
- حالة التطوير على فرع PR لا تساوي الدمج في `main`، ونجاح CI لا يساوي توقيع المؤسسة أو ترخيص الإنتاج.

## 3. الحد الأدنى لنقطة استئناف المشروع

افتح أولًا [ملخص الحالة الحالي](MCIAS_V2_CURRENT_STATE_AR.md)، ثم [دليل المطور](MCIAS_V2_DEVELOPER_START_HERE_AR.md)، ثم [سجل التنفيذ](MCIAS_V2_EXECUTION_JOURNAL_AR.md)، ثم [مصفوفة القبول](MCIAS_V2_ACCEPTANCE_MATRIX_AR.md)، ثم [تعليمات Codex](CODEX_MCIAS_V2_EXECUTION_HANDOFF.md).

بعد قراءة الملفات يجب أن يستطيع القادم الجديد الإجابة دون الاعتماد على محادثات:
- ما الهدف الفعلي؟ وما الذي يعمل الآن، وما الذي لا يعمل؟ على أي فرع وCommit؟
- أين تقع بنية البيانات والـAPI والمحركات ووكلاء AI وواجهات المستخدم؟
- ماذا اختُبر على **الإصدار الحالي تحديدًا**؟ وهل نتائج CI جديدة أم قديمة؟
- ما متطلبات الاستيراد والاعتماد والأسعار الزمنية والمخرجات الرباعية؟
- ما عوائق التشغيل والاعتماد؟ ومن صاحب القرار؟
- ما الخطوة التالية المحددة؟ وما الأمر اللازم لتشغيل اختبارات تكرارها؟

## 4. جودة التسليم لكل ميزة / وكيل

**Definition of Done** لا يتحقق إلا بعد: شيفرة قابلة للفحص، اختبارات إيجابية وسلبية وحالات حدية، عزل المؤسسة والصلاحيات، نتائج CI مع SHA، توثيق الشيفرة والتبعيات وواجهات الربط، إدخال تحديث الحالة وسجل التنفيذ، ومراجعة مستقلة. الوكلاء AI يلزمهم إضافة خط أساس، بيانات مرجعية من مختص، Precision/Recall/FPR، أمثلة أدلة وقيود الخصوصية والمصادر.

**حالات المرور:** `PLANNED` → `IN_PROGRESS` → `IMPLEMENTED_NOT_TESTED` → `TESTED_SYNTHETIC` → `REVIEWED` → `INSTITUTION_ACCEPTED`. لا انتقال تلقائي من `TESTED_SYNTHETIC` إلى `INSTITUTION_ACCEPTED`.

## 5. الفحص الآلي وحدوده

توجد `scripts/check_documentation_governance.py` و`.github/workflows/documentation-governance.yml`: يفحصان **Commits الجديدة** في طلبات الدمج و`main` ويطلبان سجلًا مهيكلًا وتحديث حالة في Commit تغيير المشروع نفسه، باستثناء تحديث سجلات التوثيق الذاتي فقط. يختبر الفحص أيضًا شكل حقول السجل.

لا يستطيع GitHub Actions منع الضغط على «حفظ» محليًا أو إرسال Commit بحد ذاته؛ سيعرض فشلًا في CI. لجعله **شرطًا يمنع الدمج مباشرة** يجب تفعيل حماية فرع `main` مع اشتراط نجاح `Documentation governance / enforce`، ومنع تجاوزها حسب الصلاحيات. **لا نفترض أن حماية الفرع مفعلة دون تحقق.**

## 6. مراجعة وتطوير السياسة

أي تعديل لهذه السياسة يحتاج تحديثًا موثقًا في السجل ونقطة الحالة نفسها وقرارًا واضحًا من صاحب المشروع إذا غيّر مستوى الحماية أو يسمح باستثناء. لا يجوز خفض مستوى الإلزام بطرق غير معلنة. لا تستخدم استثناءً صامتًا لاختبار فاشل؛ وثقه أو أوقف الدمج.

**المرجع:** DG-001 هو السياسة المشتركة لوكلاء A1–A5 وProfessor OS وكل أجزاء MCIAS ضمن المستودع. كل تكليف مستقل يجب أن يطلب الالتزام به وتسجيل خطوات العمل أولًا بأول.
