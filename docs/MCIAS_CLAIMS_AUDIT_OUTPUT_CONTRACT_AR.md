# MCIAS v2.0 — CAI-01 — عقد مخرجات تدقيق المطالبات ولوحة المؤشرات والرفض المقترح
**الحالة:** MANDATORY OUTPUT REQUIREMENTS — DRAFT FOR INDEPENDENT REVIEW; NOT IMPLEMENTED / NOT APPROVED FOR FINANCIAL EXECUTION.
**التاريخ:** 2026-10-21. **المالك:** CAI-01 تحت إشراف AI CTO. **النطاق:** عقد عرض وقرارات؛ لا تغيير في مخططات G3–G8 أو الخدمات المشتركة.
**المرجع:** تكليف CAI-01 الأصلي، ملحق Mandatory Audit Dashboard & Rejection Contract، docs/CAI01_CLAIMS_INTEGRATION_READINESS_AR.md.

## 1. تعريف وحدات الحساب والحدود
- `claim_id` هو معرّف مطالبة ثابت داخل المؤسسة؛ `claim_line_id` معرّف بندها، و`source_record_id` مع موضع `sheet_index/sheet_name/row` و`document_id/source_sha256` لإسناد المصدر. تحديد أسماء الأوراق وربط بصمتها **عقد مطلوب ولم ينفذ**؛ لا تخمين لأوراق الملخص.
- تعدّ المطالبات المميزة فقط لكل `(organization_id, claim_id)`؛ البنود والنتائج والأسباب المتعددة لا تزيد عداد المطالبات. لا تجمع ورقة الدفع/الملخص مجددًا. تقارير المبالغ تحتفظ بالعملة وبقيمة كل مطالبة ومبلغها المتأثر؛ لا خلط بين العملات ولا تحويل افتراضي.
- تتطلب كل لقطة تقرير `as_of` و`batch_ids` و`reference_version_ids` و`audit_run_id` و`snapshot_id` و`coverage_manifest`، مع عزل المؤسسة وقيود صلاحية قراءة الأدلة.
- الحالات غير المستوردة تُحصى في تسوية المصدر مستقلة عن تصنيف المطالبات؛ لا تحول الصف المرفوض في الاستيراد إلى مطالبة سليمة أو مرفوضة ماليًا.

## 2. المؤشرات الرئيسية الأربعة (لكل عملة على حدة)
1. **إجمالي قيمة المطالبات:** مجموع `claimed_amount` لبنود المطالبات الفريدة الداخلة في نطاق التقرير، مرة واحدة لكل `claim_line_id`، وفق سياسة التجميع المعتمدة، دون إضافة ملخصات الدفع. عند فقدان قيمة/عملة يعرض `UNKNOWN` مع عدد البنود الناقصة ولا تُختلق قيمة.
2. **المطالبات التي فُحصت:** عدد `claim_id` المميزة التي أكملت مجموعة الفحوص الإلزامية وفق إصدار خطة التدقيق وجرى توثيق نتائجها (بما فيها نتائج ذات ملاحظات). التنفيذ الجزئي أو غياب مرجع إلزامي لا يدخل في هذا المؤشر؛ يظهر في `unable_to_audit` أو `missing_evidence`.
3. **ملاحظات تحتاج مراجعة:** عدد المطالبات المميزة ذات نتائج مفتوحة تتطلب HUMAN_REVIEW؛ تعرض أيضًا عدد الملاحظات منفصلًا لأن المطالبة قد تحتوي على عدة أسباب.
4. **التعرض المالي المحتمل:** اتحاد نطاقات المبالغ المتأثرة `affected_line_id + amount_interval` داخل المطالبة/العملة، مع سقف مبلغ البند القابل للتأثر؛ لا تجمع المخالفات المتداخلة مرتين. عندما لا يمكن تحديد تقاطع أو مبلغ موثوق يعرض `UNQUANTIFIED` منفصلًا، ولا يحسب إجماليًا وهميًا. ليس وفرًا محققًا ولا مبلغ خصم.

## 3. التصنيفات الخمسة الحصرية ومرحلة القرار
لكل مطالبة تصنيف رئيسي **واحد فقط** عند `as_of`:
- `NO_DETECTED_FINDINGS`: كل الفحوص الإلزامية مكتملة ومرجعياتها كافية ولا توجد نتائج مفتوحة؛ لا تعني سلامة مطلقة.
- `HUMAN_REVIEW_REQUIRED`: فحوص مكتملة بما يكفي لإنتاج نتائج أو مخالفة حتمية موثقة، والقرار البشري لم يعتمد بعد؛ يتضمن التوصية الفورية بالرفض.
- `MISSING_EVIDENCE`: الأدلة اللازمة لحسم فحص إلزامي ناقصة؛ لا يجوز إعلانها سليمة أو مرفوضة تلقائيًا.
- `UNABLE_TO_AUDIT`: فشل تقني/بنيوي/مرجعي يمنع استكمال تدقيق موثوق؛ لا يجوز إعلانها سليمة.
- `HUMAN_APPROVED_REJECTION`: رفض معتمد من صاحب صلاحية بشرية، بقرار مسجل غير قابل للتعديل، بعد اكتمال متطلبات الإثبات والاعتماد.
ترتيب التصنيف: قرار رفض بشري صالح → `HUMAN_APPROVED_REJECTION`؛ وإلا تعذر الفحص → `UNABLE_TO_AUDIT`؛ وإلا نقص دليل إلزامي → `MISSING_EVIDENCE`؛ وإلا وجود ملاحظات مفتوحة → `HUMAN_REVIEW_REQUIRED`؛ وإلا اكتمال جميع الفحوص → `NO_DETECTED_FINDINGS`. عند تعارض الحالات، يحتفظ النظام بجميع النتائج الثانوية ويعرض السبب الذي حدد التصنيف الرئيسي.
- مؤشر فرعي مستقل `IMMEDIATE_REJECTION_RECOMMENDED_PENDING_APPROVAL` فقط عندما تتطابق قاعدة رفض **معتمدة وسارية** مع دليل مكتمل ومتحقق؛ يبقى التصنيف الرئيسي `HUMAN_REVIEW_REQUIRED` ما لم توجد عوائق تمنع الحسم؛ لا يغير الحالة المالية.
- `audit_status` مستقل عن `financial_decision_status` (`NOT_DECIDED/PENDING_HUMAN_REVIEW/APPROVED/REJECTED`)، والقرار المالي `REJECTED` لا يُكتب إلا بواسطة صلاحية بشرية معتمدة وخدمة الحوكمة المشتركة.
- تعرض أعداد وقيم `recommended_rejection_pending` منفصلة عن `human_approved_rejected`، وتمنع ازدواج المبالغ عند تعدد الأسباب.

## 4. قاموس أسباب الرفض الحتمي — مرشح لاعتماد القواعد لا تفعيلها
كل رمز أدناه `reason_code` مبدئي ثابت؛ الربط إلى `rule_id/rule_version` والسياسة الموقعة والسارية **شرط قبل الاستخدام**. لا توجد موافقة مؤسسية ضمن هذا المستند:
| reason_code | قاعدة الإثبات الإلزامية | حالات الحجب |
|---|---|---|
| `DUPLICATE_CONFIRMED` | نفس الحدث/البند مثبت بهوية فاتورة ومقدم ومستفيد وخدمة وتاريخ وبصمة مستند وقرار تسوية سابق؛ مع تحقق عدم كونه تصحيحًا/عكسًا/دفعة جزئية | التشابه التقريبي أو تكرار رقم بلا إثبات |
| `INELIGIBLE_AT_SERVICE_DATE` | إصدار أهلية G3 موثوق يثبت عدم الاستحقاق في وقت الخدمة، مع تطابق المستفيد والفئة والاستثناءات | هوية غير محسومة أو فجوة في المرجع |
| `DECEASED_BEFORE_SERVICE_DATE` | سجل وفاة موثوق ومخول قانونيًا، مثبت الهوية والتاريخ، ومقارنة زمن الخدمة مع استثناءات/تصحيحات محتملة | بيانات وفاة غير موثقة أو هوية ملتبسة |
| `INSURANCE_TERMINATED_AT_SERVICE` | سجل سريان/إيقاف/إنهاء تاريخي معتمد للفرد عند الخدمة، مع فترة نصف مفتوحة [from, until) | الاعتماد على حالة الاشتراك الحالية فقط |
| `CONTRACTUALLY_EXCLUDED_SERVICE` | نص استثناء G3 معتمد وسارٍ، يطابق رمز الخدمة والفئة والاستثناءات والتصاريح المسبقة | غموض البند أو استثناء غير مصدق |
| `PROVIDER_NOT_AUTHORIZED` | قائمة مقدمي الخدمة G3 سارية بتاريخ الخدمة ومجال الخدمة، مع فحص حالات الطوارئ والاستثناءات المعتمدة | مجرد عدم ظهور اسم المقدم |
| `TARIFF_REJECTION_POLICY_BREACH` | سعر/كمية/وحدة موثقة، تعرفة عقد معتمدة بتاريخ الخدمة، قاعدة سياسة موقعة تنص صراحةً على الرفض بدل التسوية | فرق سعر وحده أو تعرفة غير محسومة |
| `MATERIAL_CLAIM_INVALIDITY` | قاعدة محددة معتمدة لخطأ جوهري مثبت يمنع قبول المطالبة، موثقة بعناصرها ومعاييرها | أخطاء شكلية قابلة للتصحيح أو نقص مستند وحده |
لا يحق لقاعدة رفض افتراضية جديدة التنفيذ دون قرار مالك السياسة ومراجعة قانونية/طبية/مالية حسب الاختصاص، واعتماد G6 وتوثيق G3/G5.

## 5. سجل الملاحظة/الرفض (عقد حقول إلزامي)
`organization_id, claim_id, claim_line_id?, source_document_id, source_sha256, source_record_id, worksheet_name?, worksheet_index?, excel_row, audit_run_id, finding_id, rule_id, rule_version, reason_code, reference_id, reference_version, effective_from, effective_until, service_date, observed_value, reference_value, claimed_amount, affected_amount?, currency, evidence_refs, evidence_completeness, evidence_verification_status, system_recommendation, required_action, audit_status, financial_decision_status, reviewer_actor_id?, reviewer_authorization_ref?, reviewer_decision?, reviewer_decided_at?, reviewer_reason_code?, immutable_decision_event_id?, created_at`.
- `evidence_completeness` يوضح العناصر الإلزامية المستوفاة/الناقصة؛ `evidence_verification_status` أحد `VERIFIED/PARTIAL/UNVERIFIED/CONFLICTED`. الرفض المقترح الفوري مشروط بـ`VERIFIED` واكتمال الأدلة وقاعدة سارية معتمدة.
- `affected_amount` قيمة مثبتة أو `null`؛ لا تُساوى تلقائيًا بـ`claimed_amount`. تعرض حسابات Decimal مع العملة والتقريب والسياسة والتسلسل المرجعي. الحقول الحساسة مراجع آمنة لا تُعرض خامًا في اللوحة.
- قرار المدقق لا يعدّل الحدث السابق: إضافة حدث جديد عبر **Shared Audit Writer/G6** داخل معاملة موثوقة مع actor/time/reason/approval، وسجل append-only، مع ربط G8 للتحقق المستقل. لا تنشئ CAI-01 Writer جديدًا.

## 6. التنقل ولوحة العرض
- أربع بطاقات KPI، توزيع حصري بخمس حالات، عدّاد توصية رفض فوري مع القيمة، وعدّاد الرفض المعتمد مع القيمة؛ كل مبلغ مع العملة، والتعرض المحتمل منفصل عن الفروقات المثبتة والوفورات المعتمدة.
- كل بطاقة وتصنيف قابل للفتح بفلاتر `batch/period/provider/category/currency/audit_run` وصلاحية مؤسسة؛ من قائمة المطالبات إلى `claim_id` ثم `finding_id` ثم `rule_id/version` ثم دليل المصدر وقرار الإنسان.
- مؤشرات واضحة لنقص التغطية وعدم اكتمال الفحص؛ لا تختصر النتائج عند حد عرض الصفحات، واستخدم pagination/cursor آمنًا مع `total_count` من الخادم وتصدير مؤمن يثبت اكتمال الدفعة.
- فصل `confirmed_contractual_differences` عن `potential_exposure` عن `approved_savings` وعن `human_approved_rejected_amount`. لا تحسب رفضًا معتمدًا على أنه وفر مالي محقق إلا بدليل تسوية فعلي مستقل.

## 7. معادلات التسوية وعدم الفقد
- `received_source_rows = extracted_rows + source_extraction_failures` عندما يمكن عدّ الأصل بثقة؛ إذا تعذر تحديد عدد الصفوف الأصلية فالحالة `UNVERIFIED_SOURCE_COVERAGE`، لا صفر افتراضي.
- `extracted_rows = scoped_claim_rows + excluded_non_claim_rows + unclassified_rows` (كل سجل مرة واحدة).
- `scoped_claim_rows = imported_rows + held_rows + rejected_ingestion_rows`؛ الاستئناف لا ينشئ بنودًا إضافية، ويُسجل كل صف فاشل.
- `imported_claims = audited_complete + audit_pending_or_blocked` عند عد المطالبات الفريدة، لا الصفوف؛ يجب فصل مقياس البنود عن المطالبات.
- `classified_claims = count(distinct claim_id)`، وتوزيع الحالات الخمس يساويه تمامًا في اللقطة الموثوقة؛ إذا تعذر إكمال التسوية، تعلن اللوحة `INCOMPLETE` ولا تظهر ادعاء سلامة.
- عبر الدفعات، لا يساوي مجموع صفوف الدفع والملخص مطالبات إضافية. يجب إثبات idempotency ومطابقة المعرفات.

## 8. حالات الاختبار الاصطناعية وبوابات القبول
- SYN-DUP: تكرار مؤكد مع فاتورة أصلية/تصحيح؛ منع رفض التصحيح المشروع، وعدم ازدواج مبلغ البند.
- SYN-DEATH: وفاة موثقة قبل الخدمة، وفاة بعدها، هوية ملتبسة، وتعارض مصدرين؛ الأخيرة لا تُرفض آليًا.
- SYN-STOP: إيقاف تأمين مع تاريخ سريان وحالة إعادة تفعيل وتابع مستقل الأهلية.
- SYN-ELIG: فئة/مستفيد/تاريخ خدمة وإصدارات تاريخية معتمدة.
- SYN-TARIFF: كمية×سعر وحدة/تحمل/تقريب وفروق تعرفة، وسياسة تستوجب مراجعة أو رفضًا مقترحًا فقط عند توقيعها.
- SYN-EXCLUSION: استثناء تعاقدي مع موافقة مسبقة واستثناء للطوارئ.
- SYN-MULTI: مطالبة واحدة متعددة أسباب، حساب union للمبلغ المتأثر، لا جمع مزدوج.
- SYN-REVIEW: توصية فورية دون قرار، ثم رفض بشري مخول ومؤرخ، ثم قرار تصحيح كحدث لاحق دون محو الأصل؛ رفض محاولة مستخدم غير مخول.
- SYN-COVERAGE: صفوف مفقودة/غير صالحة، أوراق دفع/ملخص، استئناف، 10k+ صف مع قياس زمن وذاكرة وpagination/cursor وعدم truncation.
- SYN-TENANT: منع تسرب مراجع وأدلة ومراجعات بين المؤسسات.
**لم تُنفذ هذه المجموعة بعد.** اختبارات PR #31 السابقة تخص preflight فقط؛ لا يُدعى تحقق dashboard/rejection E2E.
