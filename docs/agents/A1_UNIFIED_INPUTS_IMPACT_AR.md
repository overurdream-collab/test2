# A1 — أثر متطلبات المدخلات والتدقيق الموحدة على تدقيق الفواتير
**المرجعية المعتمدة:** docs/MCIAS_UNIFIED_INPUTS_AUDIT_REQUIREMENTS_AR.md at 808a70806e6c5931b4dd5f7110e4c4d1a0a6b63e
**الحالة:** مزامنة تحليل وتصميم فقط، لا إثبات تنفيذ أو اعتماد إنتاجي.

## متطلبات ملزمة لوكيل A1
1. **زمن المرجع:** كل قراءة تاريخية تُقيّد بمؤسسة ومقدم خدمة ومستفيد وتاريخ الخدمة الفعلي. يُطبق الإصدار المعتمد الفعال نصف المفتوح `[effective_from,effective_until)`، لا أحدث نسخة وقت الإدخال أو المطالبة. إذا تداخلت نسختان أو فقد مرجع معتمد فـ`HUMAN_REVIEW/INSUFFICIENT_EVIDENCE` دون اختيار اعتباطي. النسخ المسودة لا تلغي نسخة معتمدة سابقة، والتغيير الرجعي لا يعيد كتابة نتيجة تدقيق قديمة تلقائيًا.
2. **هوية الأسرة:** الموظف مشترك أساسي ومستفيد أيضًا؛ لكل تابع `beneficiary_id` وعلاقة عائلية تاريخية، وقد يملك فئة مختلفة وتغطيات ونسب تحمل وسقوف وأهلية مختلفة. لا يرث التابع فئة الموظف أو أهليته تلقائيًا. يلزم تحديد العضوية والأهلية والفئة وإصدار التغطية لكل مستفيد بتاريخ خدمته، وربط النتائج على مستوى الفرد والأسرة والجهة مع منع عد استخدام مطالبة واحدة مرتين.
3. **مرجعية السقوف:** فصل سقف الفرد، سقف الأسرة المشتركة، سقف نوع التغطية وفترة السقف، مع حفظ الأحداث التاريخية للمطالبة والتعديل/الإلغاء/الإرجاع وعدم اشتقاق usage من تكرارات غير مستقلة.
4. **سجل التدقيق:** A1 يجب أن يصدر/يربط لاحقًا أحداث `run_started/completed/blocked`، وقراءة المصدر الطبي وفق السياسة، وإصدار النموذج والقواعد وبصمات المدخلات والمخرجات، وتوثيق دليل كل finding، وطالب المراجعة ونتيجتها، ورفض عمليات الكتابة غير المصرح بها. استخدم خدمة MCIAS الموحدة عند تنفيذها، لا تنشئ A1 AuditLog/Writer خاصًا؛ لا تُكتب أسرار/نصوص طبية خام في سجل النشاط.
5. **منع الحذف وتاريخ الإصدارات:** السجل/مرجع العقد/الفئة/التغطية يبقى append-only مع غلق/استبدال رسمي وبصمات قبل/بعد وفاعل وسبب وزمن تسجيل مستقل عن سريان التغيير. حتى السوبر أدمن لا يحذف التاريخ. A1 يعرض أصل المرجع ورقم إصداره ووقت صلاحيته للتحقق وإعادة التدقيق دون تغيير النتيجة التاريخية بصمت.
6. **المسؤولية المالية:** ناتج A1 `HUMAN_REVIEW` أو نقص أدلة، لا رفض/خصم/اعتماد/وفورات G7؛ التوقيع الإلكتروني المؤسسي مؤجل. تحرير العقود والمرجعيات للسوبر أدمن فقط عند تنفيذ ضبط التهيئة والتسليم؛ عدم اعتبار ذلك مفعلا في API الحالية.

## الحالة الحالية والفجوات
- **متوفر جزئيًا ومثبت سابقًا:** G2 أصل مشفر وبصمة وlocator؛ A1 مصادر line-item وDecimal، `a1_input_fingerprint`/output، historical G3 provider tariff تشخيصي بتاريخ الخدمة، مخرجات G6 `HUMAN_REVIEW` دون سلطة مالية.
- **غير متحقق بعد في A1:** لقطة زمنية موحدة للموظف والتابعين وعلاقات الأسرة وتواريخ الفئات والتغطيات والسقوف؛ حسم تاريخ إسناد الفئة لكل فرد؛ احتساب استخدام سقوف بلا ازدواج؛ خدمة audit مشتركة شاملة ومحصنة ونسخ أثر التدقيق؛ إشعار مراجعة بشرية منسق عند السعر المفقود (المدخل الحالي يفشل إغلاقًا).
- **اعتماديات فروع منفصلة:** PR22 ReferencePoint وإغلاق الإصدارات لا يُعتبران مدمجين أو مرجعًا ماليًا معتمدًا؛ مستجدات عقود/مدخلات PR25/المدخلات الموحدة لا تدخل PR20 آليًا. اختيار المراجع الزمنية وسجل الأسرة والتدقيق المشترك يجب أن يقدم من النظام المركزي مع اختبارات tenant/RBAC وتعارض الإصدارات.
- **عائق قبول:** لا يجوز إثبات حساب سقف الأسرة/الأهلية من نموذج G3 التاريخي البسيط، ولا افتراض توفر البيانات أو إصدار قرار مالي قبل إتاحة مصدر صريح ومختبر.

## اختبارات قبول مستقبلية (غير منفذة بهذا التغيير)
- تاريخ خدمة قبل/عند/بعد انتقال نسخة عقد أو تغطية؛ حالة نهاية النطاق الحصرية؛ مسودة بديلة لا تحجب النسخة السارية؛ فترتان متداخلتان => مراجعة لا تخمين.
- موظف وزوجة وابن بفئات وتغطيات وأهلية وسقوف مختلفة؛ إيقاف عضوية أحدهم دون إسقاط البقية تلقائيًا؛ مطالبات الأسرة دون ازدواج الاستخدام.
- audit event يربط run/actor/tenant/evidence/ref versions والوقت الفعلي؛ فشل معاملات القراءة/الكتابة والتحقق من السريّة؛ لا حذف للتاريخ ولا مفاتيح طبية خام في السجل.
- حالات سعر الفاتورة المفقود والحساب المتعارض تستمر كقضايا مراجعة ولا تتحول إلى قرارات G5/G7.

## ترتيب التكامل عند توافر الخدمات المشتركة
أولًا API قراءة موثوق للمرجع الساري بتاريخ الخدمة مع هوية الأسرة والإصدارات، ثم سجل audit موحد ومصدر أدلة غير متغير، ثم اختبارات عبور المؤسسة والنسخ والتعارض، ثم دمج قراءة فقط في A1. لا بناء صلاحيات/توقيع/سجل تدقيق مستقل.
