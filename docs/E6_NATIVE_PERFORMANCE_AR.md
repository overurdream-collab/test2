# E6 — قياس المسار الأصلي ببيانات اصطناعية

الحالة بعد تشغيل المشرف: **INTEGRATION VERIFIED** ضمن عينات القياس الاصطناعية المحدودة فقط. هذا قياس محدود للأداء وصحة التتبع أثناء القياس، ولا يعيد مجموعة الحقيقة المعروفة ذات24 حالة ولا يمنح اعتمادًا إنتاجيًا.

## النطاق وطريقة التشغيل

الأداة `scripts/benchmark_inputs_first.py` تستدعي خدمات G2 وG4 وG3 وG5 وShared Audit وG6 القائمة. لا تستورد المطالبات مباشرة إلى قاعدة البيانات ولا تصنع شهادات G3. تنشئ فقط ملفات مصادر اصطناعية، ثم يوافق Super Admin الاصطناعي على النطاق والمرجعيات عبر الخدمات نفسها.

لكل عينة10 أو25 أو100 مطالبة: ملف Excel بورقتي CLAIMS وPAYMENT، وستة ملفات CSV للمرجعيات، وملف تنفيذ خدمات. لكل مطالبة مستفيد مستقل؛ لذلك لا يُفترض استهلاك مشترك للسقف بين مطالبات العينة. توجد سجلات تاريخية لخدمة أخرى، وسجل كامل معلن للفترة من2026-01-01 حتى2026-07-01، والخدمة بتاريخ2026-06-01. سياسة الصرف تطلب نافذة30 يومًا يغطيها المرجع. سيناريو القياس المتوقع MATCH_VERIFIED لجميع المطالبات؛ لا يقيس Precision أوRecall أو جودة OCR.

```bash
MCIAS_BENCHMARK_ALLOW=YES \
MCIAS_ENVIRONMENT=development MCIAS_MALWARE_SCAN=disabled \
PYTHONPATH=. /workspace/security-venv/bin/python \
  scripts/benchmark_inputs_first.py --sizes 10,25,100 --max-seconds 300 \
  --output docs/evidence/E6_NATIVE_PG16_BENCHMARK.json
```

يُزود المشرف `MCIAS_BENCHMARK_DATABASE_URL` سرًا في البيئة. تقبل الأداة `postgresql+psycopg` على loopback فقط وقاعدة `mcias_benchmark_inputs`، وترفض query parameters. لكل حجم عملية Python جديدة وschema عشوائي مستقل، وتُحذف schema بعد إعادة القراءة بعدCommit. إنشاء الجداول عبر ORM metadata داخل schema قياس معزولة؛ ليس هذا اختبار ترحيل Alembic. حد العينة300 ثانية، والاستعلام20 ثانية وانتظار القفل3 ثوانٍ؛ يتوقف توسيع الأحجام عند أول فشل.

## تفسير المقاييس

- عدد الملفات والصفوف الخام والمطالبات والورقتين مقاس من المصادر وخدمات الإدخال؛ PAYMENT مستبعد من ClaimEntry.
- `perf_counter` يقيس الزمن الجداري. يقيس G2 لكل المصادر، وG4 اعتماد النطاق والتطبيع، وإعداد المصادر المرجعية واعتمادها، وربط دليل التنفيذ، وG5، وG6، وإعادة القراءة والتنظيف.
- قياس G3 الحقيقي متداخل داخل فحص G5 الحقيقي. الفرق بين الفحص وG3 يسمى **القواعد والتحقق من المصدر**، والفرق بين G5 والفحص يسمى **الحفظ والتنسيق**. هذا الأخير يشمل fingerprint والصلاحيات والحفظ وCommit؛ ليس زمن Shared Audit وحده.
- أزمنة إعداد المراجع ودليل التنفيذ تشمل إدخال ملفاتها في G2؛ لا يجوز جمع جميع حقول الزمن بسبب التداخل. `pipeline_wall_seconds` هو زمن المسار نفسه، ويستبعد schema setup والتحقق الختامي وإعادة المحاولة والتنظيف.
- `process_time` يقيس CPU العميل من بدء عينة قاعدة البيانات حتى تنظيفها، بعد استيراد وحدات Python. CPU عمليات parser التابعة منفصل عبر `RUSAGE_CHILDREN`. ذاكرة العميل هي Linux `ru_maxrss*1024` طوال عملية جديدة لكل حجم؛ أعلى ذاكرة لعملية parser منفردة منفصلة وليست مجموع العمليات. لا تُقاس هنا ذاكرة أوCPU خادم PostgreSQL.
- تعرض الأداة counts فعلية لصفوف الشهادات العائدة من G3 والصفوف التي يعيد `source_scope` فحصها أثناء التدقيق الأول فقط. تسمح هذه العدادات بكشف عمل متزايد تربيعيًا دون افتراضه من زمن ثلاث عينات.
- يُعاد إدخال Excel نفسه مرة، وإعادة G5 وفتح G6 للمطالبتين الأولى والأخيرة. يجب ثبات تعداد المستندات والمطالبات والنتائج والأحداث والحالات وholds بعدCommit. لا يُعاد طلب hold لأنه قرار مستقل قابل للإلحاق.
- `human_review_flag` يعكس العلم الاستشاري في snapshot؛ جميع snapshots تظل held ولا payable. نسبة UNRESOLVED مستقلة عنه. إحالة G6 hold لا تمثل قرارًا ماليًا أو مراجعة بشرية منفذة.

## النتائج المثبتة

اختبارات الحواجز والمعادلات وبيانات المصادر فقط: **20 PASS** في0.31 ثانية. شغّل المشرف الدفعة المركزية على PostgreSQL16.15، مع بقاء سكربت المالك ثابتًا بالبصمة المعلنة. توقف وكيل القياس بسبب حد الاستخدام بعد تجهيز الأداة، فأكمل المشرف التحقق والحفظ دون إعادة تشغيل العينات الناجحة.

لا SLA ولا استقراء لقدرة ملفات ضخمة من هذه الأحجام، ولا تحويل للقيمة المالية200 مليون إلى عدد مطالبات. التزامن، ذاكرة خادم قاعدة البيانات، OCR، وتحسين القراءة العربية خارج هذا القياس. لا تغيير لخدمات الإنتاج ولا قواعد التدقيق ولا الحدود المالية أو سياسات الصلاحيات.
