# G9 — دليل التعافي من الكوارث والتحقق من الاستعادة

**الحالة:** إجراء تشغيلي مقترح — لا توجد شهادة نجاح للاستعادة على خوادم المؤسسة حتى الآن.

## المبادئ الأساسية

يجب أن تشمل النسخة الاحتياطية **قاعدة PostgreSQL ومخزن الملفات الأصلية المشفرة وبصماتها ونسخ السياسات وإعدادات الاعتماد**. لا يكفي نسخ قاعدة البيانات وحدها. تحفظ مفاتيح التشفير والتحقق لدى جهة منفصلة عن الملفات الاحتياطية، وفق إجراءات استرداد موثقة ومزدوجة الاعتماد.

يمنع استخدام مفتاح تشفير من مشروع تجريبي أو تخزين المفاتيح في GitHub أو مشاركتها داخل سجل تنفيذ الأوامر.

## إجراء الاستعادة التجريبي الإلزامي

1. يسجل مسؤول الاستعادة رقم النسخة الاحتياطية وتاريخها وموقعها وبصمة SHA-256 ونسخة البرنامج ونسخة PostgreSQL والإصدارات المطبقة من Alembic.
2. يوقف إدخال البيانات إلى بيئة الاختبار، ويحفظ سجلات الحادث، ويتحقق من هوية المسؤولين المخولين بالاستعادة.
3. يوفر خادماً **معزولاً ومستقلاً** عن قاعدة البيانات الحية، مع PostgreSQL مماثل أو متوافق واعتمادات منفصلة.
4. يتحقق من سلامة أرشيف النسخ الاحتياطية وتوقيعه/سند المصدر إن كان موجوداً، ثم يفك تشفير النسخة في مساحة محمية. أي فشل SHA-256 أو AES-GCM يوقف العملية.
5. يستعرض محتويات تفريغ PostgreSQL قبل الاستعادة: `pg_restore --list database.dump`.
6. ينشئ مسؤول قاعدة البيانات قاعدة اختبار جديدة بالاسم المعتمد محلياً، مثل `mcias_restore_validation`، ثم ينفذ على **القاعدة المعزولة فقط**:

```bash
pg_restore --exit-on-error --no-owner --no-privileges \
  --dbname=mcias_restore_validation database.dump
```

7. يراجع نتيجة `SELECT version_num FROM alembic_version;`، وعدد المطالبات وأدلة المصدر والتدقيق والتقارير وإصدارات G8، ويقارن نتائج الاستعلامات بأرقام النسخة الاحتياطية.
8. يعيد ملفات المصدر المشفرة إلى مخزن **اختبار**، ويفتح عينات معتمدة باستخدام المفاتيح المؤسسية الصحيحة ويقارن بصمة كل ملف بالقيمة الأصلية. يجب اختبار حالات التلاعب والملفات المفقودة والمسارات غير الآمنة.
9. يقيس زمن الاستعادة الفعلي، ويفحص فقدان البيانات المتوقع (RPO)، ويقارن بـ RTO/RPO المكتوبين والمعتمدين من المؤسسة.
10. يوقع مسؤول أمن مستقل ومالك البيانات على نتيجة التجربة. لا يسمح بالانتقال إلى الإنتاج أو استبدال بيئته قبل موافقة استعادة منفصلة وخطة رجوع محددة.

## أدلة إلزامية للقبول

| الدليل | المطلوب | الحالة |
|---|---|---|
| أصالة النسخة | مصدر مستقل، سلسلة حيازة موثقة وبصمة ملفات | بانتظار التحقق المؤسسي |
| قاعدة البيانات | نسخة مستقلة ومتكاملة مع الإصدار الصحيح | اختبارات CI اصطناعية فقط |
| الملفات المشفرة | استعادة فعلية وفحص SHA-256 للمحتوى الأصلي | اختبارات CI اصطناعية فقط |
| الأداء | مدة فعلية، حجم بيانات المؤسسة، RTO وRPO المعتمدان | غير متوفر |
| الأمان | صلاحيات ضيقة ومفاتيح منفصلة وسجل وصول | بانتظار الفحص |
| التوقيع | توقيع مسؤول البيانات ومسؤول أمن مستقل | غير متوفر |

## مسار الفشل

إن فشل التشفير أو فحص البصمة أو ظهرت نسخة ناقصة، تُوسم النسخة بكونها غير قابلة للاعتماد ويمنع تشغيلها. يتم الرجوع إلى نسخة أقدم **فقط بعد التحقق من سلامتها**، وتوثيق أثر فقدان البيانات، وإبلاغ مسؤول المؤسسة. لا تُعدّل ملفات المصدر الأصلية لمعالجة فشل الاختبار.

## ما تثبته اختبارات المشروع وما لا تثبته

اختبار T17 في GitHub يثبت إمكانية إنشاء تفريغ PostgreSQL اصطناعي وتشفير حزمة واستعادتها في قاعدة أخرى مع فحص ملفات مصدر مشفرة. لا يثبت الاستعادة من خادم المؤسسة، ولا التوافر بعد تعطل القرص، ولا استرداد المفاتيح بعد ضياع المسؤول عنها، ولا توافق الجهاز أو قابلية الوفاء باتفاقية استعادة معتمدة.

**تبقى بوابة G9 مفتوحة حتى تنفيذ تمرين استعادة مستقل على البنية المستهدفة وتوقيع نتائجها.**
