## 4. ترتيب تنفيذ Codex — فقط إغلاق تجربة اللابتوب

1. **استئناف بلا تعارض:** اقرأ أحدث HEAD/CI لفرع PR #34 ولـPR #25، وافحص ownership/diff قبل أي نقل. لا تعِد اختبارات النجاح لمجرد تحديث الوثائق.
2. **أقل واجهات عملية:** وفّر للمراجع شاشات إدخال/اعتماد المدخلات الأساسية باستخدام ما يصلح من PR #25؛ وأزل الحاجة إلى كتابة JSON لتصنيف أوراق Excel واختيار معرفات يدوية في الرحلة الأساسية قدر الإمكان. لا تُنشئ منصة UI جديدة أو صفحات إدارة غير لازمة.
3. **رحلة المتصفح الحقيقية:** حساب مسؤول مُهيأ بأمان وMFA؛ تجهيز المرجعيات الست تاريخيًا؛ رفع XLSX؛ تصنيف CLAIMS/PAYMENT/FAMILY_SUMMARY؛ preview/resume؛ تشغيل G5؛ مراجعة مستقلة G6؛ لوحة G7 والتصدير. اختبر الرفض الآمن عندما تغيب المرجعيات أو الصلاحيات.

5. **اختبار التسليم:** تحقق من بدء نظيف، تسجيل الدخول وTOTP، رفع XLSX اصطناعي، إعادة التشغيل مع بقاء البيانات، النسخ الاحتياطي/الاستعادة على نسخة اختبار، ومراجعة أحداث G6/G7. إذا لم تتوفر آلة Windows 11، ضع النتيجة `WINDOWS_NOT_VERIFIED` وقدم تعليمات تجربة المستخدم بدل الادعاء.
6. **التسليم:** رابط artifact + SHA256 + HEAD + ملخص CI المطابق + قائمة خطوات إعادة الإنتاج + أي عائق حقيقي. لا تسلم تقريرًا فقط.

## 5. معيار القبول الصريح

`PILOT_READY` فقط عندما تكون الحزمة قابلة للتنزيل، والإقلاع الآمن يعمل، ويمكن للمستخدم إكمال الرحلة من واجهات المتصفح دون استدعاءات API يدوية، مع أدلة التشغيل والبيانات الاصطناعية. خلاف ذلك `PILOT_BLOCKED` مع العائق المحدد. النجاح الاصطناعي السابق = `INTEGRATION_VERIFIED` ولا يساوي `PILOT_READY` أو `PRODUCTION_ACCEPTED`.
