# MCIAS v2.0 — قرار معتمد: اعتماد السوبر أدمن دون توقيع إلكتروني مستقل

**التاريخ:** 2026-10-18
**صاحب القرار:** مالك المشروع
**الحالة:** قرار نهائي ملزم لجميع الوكلاء والواجهات والتكاملات.
**النطاق:** العقود، البنود، المرجعيات، الرسوم/التعرفات، والمدخلات التي تستدعي اعتمادًا مركزيًا، ضمن الصلاحيات التي يحددها النظام.

## القرار

1. **يُستبعد تمامًا من نطاق المشروع تنفيذ أي منظومة توقيع إلكتروني مؤسسي مستقلة**: لا شهادات رقمية، لا PKI، لا توقيعات مشفرة للمستندات، لا تكامل مع مزود توقيع خارجي، ولا اشتراط توقيع رقمي على مرجع الرسوم أو التعرفة أو بنود العقد.
2. **الإجراء الإداري المعتمد داخليًا هو موافقة السوبر أدمن من خلال حسابه الموثق وصلاحيات الخادم**. يمثل السوبر أدمن سلطة الاعتماد المؤسسي داخل MCIAS. تسمى العملية `super_admin_approval` أو «اعتماد السوبر أدمن» وليس «توقيعًا رقميًا موثوقًا قانونيًا».
3. لا يجوز أن يعتمد AI أو مسؤول الجهة أو مستخدم عادي أي شرط أو تعرفة أو مرجع يتطلب موافقة السوبر أدمن. تفويض إدارة المستفيدين، إن سُمح به، لا يتضمن تفويض صلاحيات اعتماد العقود.
4. يجب أن يتحقق الخادم من الهوية الفعلية ودور السوبر أدمن والصلاحية ونطاق المؤسسة والحالة والتعارضات وتواريخ السريان **قبل الاعتماد**؛ لا تكفي إظهار زر بالواجهة ولا الحقول التي يرسلها العميل.
5. يسجل Audit Log المشترك حدث الاعتماد ومحاولات الرفض: `actor_id`، المؤسسة، `resource_id`، الإصدار والبصمة المرجعية أو hash إن وجد، التوقيت، القرار، الحالة السابقة والجديدة، وتاريخ السريان، دون أسرار أو بيانات طبية حساسة. لا يجوز حذف أو تغيير الحدث من أدوار التطبيق.
6. تحفظ مسودة المصدر والأدلة والتصحيحات والإصدارات السابقة؛ يحظر تحويل استخراج AI مباشرة إلى اعتماد أو قاعدة مالية مفعلة، ويستمر HUMAN_REVIEW حيث يلزم.
7. **لا اشتراط لأي توقيع إلكتروني أو توقيع مؤسسي مستقل في اختبارات القبول أو خطط التنفيذ أو تكليف الوكلاء**. أي وثيقة قديمة تذكر `institutional signature` أو `signed fee reference` لا يجوز تفسيرها كشرط تنفيذ؛ يستعاض عنها بسلطة اعتماد السوبر أدمن الموثقة داخليًا.
8. هذا **قرار صلاحية وإجراء داخلي داخل النظام**، ولا يقدم ادعاءً بأن ضغط زر الاعتماد يعادل توقيعًا قانونيًا خارج النظام. إذا نشأ لاحقًا التزام قانوني خارجي محدد، يُرفع لصاحب المشروع كمسألة منفصلة، ولا يُنشأ تلقائيًا نظام توقيع جديد.

## معايير قبول التنفيذ لاحقًا

- مستخدم غير سوبر أدمن يُرفض من API حتى لو تلاعب بالواجهة، وتسجل المحاولة وفق سياسة Audit.
- حساب سوبر أدمن مصادق عليه يملك صلاحية اعتماد صريحة، يخضع لفحص المرجعيات والأدلة قبل تغيير الحالة.
- تسجل هوية المعتمد والإصدار والوقت وتاريخ السريان، وتبقى النسخ السابقة.
- يمنع اعتماد AI تلقائيًا، ولا تُنشأ تبعية لشهادة/مفتاح/مزود توقيع.
- لا يُدّعى أن هذه الضوابط منفذة في كل المسارات قبل ظهور أدلة الاختبار.

## مسؤولية التطبيق

- **PR #25 / مالك الخدمات المشتركة:** تحديد/اختبار عقد الاعتماد وتسجيله وRBAC المشترك عند تكليف التنفيذ.
- **PR #23 / Contract Intelligence:** اقتراحات بشرية فقط؛ لا متطلب لتوقيع إلكتروني.
- **PR #20 / A1:** استهلاك المرجع المعتمد وفق تاريخ الخدمة، وعدم اشتراط signed reference أو اتخاذ قرار مالي آلي.
- **مشرف المشروع:** إبقاء هذا القرار مرجعية أعلى من التعليمات التاريخية المتعارضة، مع تعديل الوثائق الفرعية في دوراتها القادمة دون دمج فروعها الآن.
